## 1. 위협 모델

### 1.1 보호 자산

| 자산 | 위치 | 유출 시 영향 |
|---|---|---|
| 신원 개인키 `sk` (secp256k1, 32B **원시 바이트**) | 폰 IndexedDB `meta.identity` | 사칭 + 모든 신규 대화 복호 = 전면 붕괴 |
| 래칫 프리키 개인키 `spkPriv` (P-256, non-extractable) | 폰 IndexedDB | 첫 왕복 이전 메시지 복호 |
| 더블 래칫 세션 상태 (`rk`, `cks`, `ckr`, `skipped`) | 폰 IndexedDB `sessions` | 진행 중 대화 복호 |
| 메시지 평문 | 폰 IndexedDB `messages` (평문 저장, 의도된 결정) | 대화 내용 유출 |
| 소셜 그래프·타이밍 메타데이터 | 릴레이 / 맥 헬퍼 | 누가·언제·얼마나 |

### 1.2 공격자 모델

| # | 공격자 | 능력 |
|---|---|---|
| A1 | **네트워크 도청자** | 릴레이까지의 트래픽 관찰 (TLS로 차단됨) |
| A2 | **악성/탈취된 릴레이** | 암호문·메타데이터 열람, 임의 삭제·지연·재정렬·재생 |
| A3 | **탈취된 맥(헬퍼/릴레이)** | A2 + 로컬 디스크 전체 + 푸시 발송 능력 |
| A4 | **악성 연락처** (상대가 클라이언트를 개조) | 임의의 유효 서명 페이로드 전송 |

| A6 | **폰 물리적 탈취** | IndexedDB 전체 (앱 잠금 없음 — 명시적 비목표) |

### 1.3 신뢰 경계 — 이 감사의 핵심 결론

현재 설계는 **두 개의 완전히 다른 역할**을 뭉뚱그려 "서버"라고 부르고 있고,
이 둘의 신뢰 요구는 정반대다.

| 역할 | 하는 일 | 신뢰가 필요한가 | 맥에 둬도 되나 |
|---|---|---|---|
| **역할 A — 코드 오리진** | HTML/JS를 브라우저에 전달 | **절대적으로 필요.** 오리진이 곧 앱이다. | ❌ **불가** |
| **역할 B — 메시지 릴레이** | 암호문 저장·중계 | **불필요.** E2EE가 방어한다. | ✅ **권장** |

> **불변식 #1**: 역할 A와 역할 B는 서로 다른 신뢰 도메인에 있어야 한다.
> 둘을 한 상자에 합치는 순간, 그 상자 하나가 시스템 전체의 단일 신뢰 루트가
> 되고 "서버가 탈취돼도 안전하다"는 명제는 **수학적으로 성립하지 않는다**.

이 불변식이 사용자의 두 요구("맥을 서버로", "맥이 털려도 괜찮게")를 동시에
만족시키는 유일한 길이다. 자세한 논거는 §4.

## 3. 상세 분석

### F-01 [Critical] 코드 오리진이 무제한 신뢰 루트

**사실관계.** `index.html`에 `Content-Security-Policy` 메타가 전혀 없다.
`js/crypto.js:23`의 `generateSecretKey()`는 nostr-tools가 요구하는 대로
**원시 32바이트**를 반환하고, 이것이 `store.js`를 통해 IndexedDB에 그대로
저장된다(P-256 프리키만 `extractable:false`인 `CryptoKey`다).

**영향.** 오리진에서 실행되는 임의의 JS 한 줄이 IndexedDB에서 `sk`를 읽어
외부 서버로 반출할 수 있고, CSP가 없으므로 `connect-src`·`img-src` 등
어떤 채널로도 막히지 않는다. 이는 A5(오리진 탈취)뿐 아니라, 향후 어떤 경로로든
XSS가 생기면 즉시 전면 붕괴로 이어진다는 뜻이다.

**현재 잘 되어 있는 점**: 렌더링은 전부 `textContent`를 쓰고 `innerHTML`
주입 지점이 없다(`main.js`의 말풍선·연락처·안전코드 전부). 즉 *지금은* XSS
진입점이 없다. 문제는 방어선이 그것 하나뿐이라는 것 — 심층 방어가 없다.

**한계에 대한 정직한 진술.** CSP는 반출 경로를 좁힐 뿐, **오리진을 완전히
장악한 표적 공격자를 막지 못한다.** 그런 공격자는 CSP 메타 자체를 고쳐서
서빙한다. 웹앱에서 오리진 신뢰는 제거 불가능하다(§4 참조).

---

### F-02 [High] 헬퍼의 30일 암호문 아카이브

**사실관계.** `helper/helper.mjs`의 `handleWatchedEvent()`는 감시 대상 wrap을
전부 `state/archive.jsonl`에 `{id, event, firstSeenAt}` 형태로 append하고,
`pruneAndRepublish()`가 24시간마다 30일 이내 항목을 릴레이에 재발행한다.
`state/subs.json`에는 두 사용자의 푸시 엔드포인트와 `auth` 비밀이 있다.

**영향(A3, 맥 탈취).** 공격자는 30일치의 완전한 통신 메타데이터
(누가·언제·몇 건)와 암호문 더미를 한 번에 얻는다. 더블 래칫 덕분에 첫 왕복
이후 메시지는 신원키가 유출돼도 안전하지만, **첫 왕복 이전 구간**
(PLAN.md §2에 명시된 PFS 예외)은 정적 ECDH 수준 보호뿐이라 *미래의* 폰
탈취와 결합하면 평문이 된다. 즉 아카이브는 전형적인
**harvest-now-decrypt-later 저장고**로 기능하며, 하필 보안 업데이트가 끝난
macOS 11 상자 위에 놓여 있다.

**구조적 관찰.** 릴레이를 맥으로 옮기면 이 아카이브는 **릴레이 저장소와
완전히 중복**된다. 역할 재배치만으로 자연스럽게 제거할 수 있다.

### F-03 [High] 세션 직렬화가 탭 내부에만 존재

**사실관계.** `main.js:417-422`의 `enqueueSessionOp`은 **모듈 스코프의
프로미스 체인 하나**다. M2/M4에서 고친 경합은 "한 탭 안에서의 동시 실행"이었고,
그 수정은 정확했다. 그러나 이 큐는 프로세스(정확히는 문서) 로컬이다.

**영향.** 같은 앱이 두 개의 문서 컨텍스트에서 열리면
(설치된 PWA + 브라우저 탭, 데스크톱 다중 창, iOS에서 Safari와 홈화면 앱 병행)
각 컨텍스트가 **독립된 큐와 독립된 IndexedDB 연결**을 갖는다. 두 컨텍스트가
같은 상대에게 동시에 `getSession → managerEncrypt → saveSession` 을 수행하면
나중에 끝난 쪽이 앞선 래칫 전진을 덮어쓴다. 결과는 **해당 대화의 영구
복호 불능** — M4에서 관측했던 "메시지 하나가 delivered로 안 넘어감"의
심화판이다.

`store.js`의 `getSession`과 `saveSession`이 **서로 다른 IndexedDB 트랜잭션**
이라는 점도 같은 문제의 다른 얼굴이다. read-modify-write 전체가 원자적이지 않다.

### F-04 [High] 래칫 비동기화 시 영구 복구 불가

**사실관계.** `pfs.js:26` `MAX_SKIP = 256`. `skipMessageKeys()`는
`until - st.nr > MAX_SKIP`이면 예외를 던지고, `sessDecrypt`는 사본에서
작업하다 실패 시 원본 상태를 **커밋하지 않는다**(이 설계 자체는 옳다 —
변조 메시지가 상태를 오염시키지 않는다).

**영향.** 연속 256건을 놓치면(릴레이 장기 장애 + 헬퍼 아카이브 만료, 또는
오래된 백업에서 복원) 이후 모든 메시지가 영구히 복호 실패한다. 상태가
전진하지 않으므로 **스스로 회복되지 않고**, 앱에는 세션을 초기화할 UI가
전혀 없다. 사용자 입장에서는 "대화가 그냥 죽었다".

**참고.** 이는 기밀성 문제가 아니라 **가용성** 문제지만, 복구 수단이 없다는
점에서 심각도가 높다. 그리고 A3(탈취된 맥이 유일한 릴레이가 되는 신규
아키텍처)에서는 공격자가 **의도적으로 유발할 수 있는** 상태가 된다.

### F-05 [Medium] 대화 간 격리 부재

**사실관계.**
- `main.js:502`: `await updateMessageStatus(payload.ref, "delivered");`
- `store.js`의 `updateMessageStatus(id, status)`는 `messages`를 **전역
  기본키 `id`로만** 조회한다. 발신자가 그 메시지의 상대인지, `dir === "out"`
  인지 **확인하지 않는다.**
- 같은 구조로 `main.js:480`의 `hasMessage(payload.id)`도 전역 조회다.

**영향(A4, 악성 연락처).** 연락처 B가 `{kind:"ack", ref:X}`를 보내면, X가
연락처 C와의 대화에 속한 메시지여도 `delivered`로 바뀐다. 수신 메시지의
상태도 덮어쓸 수 있다. UUIDv4를 추측할 수 없으므로 실전 악용 난도는 높지만,
**권한 검사 자체가 없다**는 점이 결함이다. 또한 `id`가 전역 기본키이므로
서로 다른 대화 간 `id` 충돌 시 `addMessage`의 `store.add()`가
`ConstraintError`로 실패해 정상 메시지가 유실될 수 있다.

---

### F-06 [Medium] 수신 페이로드 검증 부재

**사실관계.** `main.js:476-484`는 복호된 페이로드에 대해 `payload.v !== 3`과
`payload.kind` 분기만 검사하고, 다음을 **그대로 신뢰**한다.

| 필드 | 현재 검증 | 악용 |
|---|---|---|
| `body` | 없음 (타입·길이 무검증) | 수십 MB 문자열 → IndexedDB 고갈, 렌더링 정지 |
| `ts` | 없음 | 먼 미래 값 → 히스토리 최하단 고정(§6.5는 `ts` 오름차순 정렬), 먼 과거 → 최상단 은닉 |
| `id` | 없음 | 임의 문자열이 IndexedDB 기본키가 됨 |
| `ref` | 없음 | F-05와 결합 |

2000자 제한은 **발신 UI에만** 존재하고(PLAN.md §14 기본값), 수신 경로에서는
한 번도 강제되지 않는다. 개조 클라이언트를 쓰는 연락처는 이 제한을 무시한다.

---

### F-07 [Medium] 중복 수신 시 ack 미재전송 → 전달확인 교착

**사실관계.** `main.js:480`의 `if (await hasMessage(payload.id)) return;` 은
**ack 전송(485-494행)보다 먼저** 반환한다.

**시나리오.** A가 발신 → B가 저장 → B의 ack가 릴레이에서 유실. A는 영원히
✓ 상태. A가 ⚠/재전송을 눌러 같은 `id`로 재발행 → B는 중복으로 판정하고 즉시
반환 → **다시는 ack를 보내지 않는다.** A는 어떤 방법으로도 ✓✓에 도달할 수
없고, 사용자는 "안 갔나 보다" 하며 반복 재전송한다. M3에서 구현한
재전송 기능이 이 경우에 무력화된다.

---

### F-08 [Medium] `seenWraps` 선기록으로 인한 메시지 영구 유실

**사실관계.** `main.js:446-447`:
```js
if (await hasSeenWrap(rawEvent.id)) return;
await markSeenWrap(rawEvent.id);      // ← unwrap·복호·저장보다 먼저
```

**영향.** 이 시점 이후 어디서든 실패하면(탭 종료, IndexedDB 쓰기 실패,
예기치 못한 예외) 해당 wrap은 **영구히 "처리됨"으로 남고**, 다음 구독
재생 때 다시 처리되지 않는다 → 메시지 조용한 유실. 릴레이가 재발행해도
소용없다. 현재는 `startMessaging`의 `.catch()`가 예외를 삼키므로 사용자는
유실 사실조차 모른다.

부수적으로 `pruneSeenWraps`(7일)와 헬퍼 재발행(30일)의 불일치로, 7일 지난
wrap이 재발행되면 재처리 → pfs 리플레이 방어에 걸려 폐기된다. 무해하지만
낭비다.

### F-09 [Medium] 세션 락 내부의 네트워크 발행

**사실관계.** `sendTextLocked`(`main.js:435`)와 수신 ack 경로
(`main.js:491`) 모두 `await net.publishWrap(...)`을 `enqueueSessionOp`
**내부에서** 수행한다. `AbstractRelay`의 `publishTimeout`은 4400ms다.

**영향(A4).** 수신 메시지 1건마다 ack 발행이 전역 락 안에서 최대 4.4초를
점유한다. 악성 연락처가 메시지를 쏟아부으면 (암호 연산 + IndexedDB 쓰기 +
네트워크 왕복) × N이 한 줄로 직렬화되어, **다른 모든 대화와 사용자 본인의
발신까지 정지**한다. 증폭 계수가 1:1이라 대규모 DoS는 아니지만, 단일 큐라는
설계상 영향 범위가 앱 전체다.

---

### F-10 ~ F-16 (요약)

- **F-10** `crypto.js:68`의 이름 검증은 길이(1~20)뿐이다. `U+202E`(RTL
  override) 등 양방향 제어문자·제로폭 문자가 통과해 연락처 목록과 채팅
  헤더에서 **다른 연락처를 시각적으로 사칭**할 수 있다. `textContent`를
  쓰므로 XSS는 아니지만, 안전코드 기반 신뢰 모델을 UI 층에서 우회한다.
- **F-11** `pfs.js:27` `MAX_SKIPPED_STORE = 512`. 세션당 최대 512개의
  **살아있는 메시지 키**가 TTL 없이 IndexedDB에 남는다. 기기 탈취 시 미도달
  메시지들이 복호된다 — PFS의 부분적 잠식.
- **F-12** 신원키 원시 저장은 nostr-tools/secp256k1의 요구사항이며
  WebCrypto에 secp256k1이 없으므로 **회피 불가**. 대응은 키 비추출성이 아니라
  피해 반경 축소(CSP)와 at-rest 암호화여야 한다.
- **F-13** meta 태그 CSP는 `frame-ancestors`를 지원하지 않으므로, 프레임
  삽입 방어는 JS 측 검사가 필요하다. 현재 없음.
- **F-14** 래칫 헤더에 `n`/`pn` 카운터가 있음에도 앱은 수신 갭을 전혀
  계산하지 않는다. 릴레이(=신규 아키텍처의 맥)가 메시지를 **조용히 삭제**해도
  양쪽 모두 알아채지 못한다. Zero Trust 릴레이에서는 반드시 닫아야 할 구멍이다.
- **F-15** `net.js`의 재연결은 부팅 시 계산한 `since`를 재사용한다. 경계가
  있어 보안 문제는 아니나, 장시간 구동 시 중복 수신이 늘어난다.
- **F-16** 헬퍼는 `pushsub` DM을 발신자 pk별로 무조건 덮어쓴다. 릴레이가 과거
  등록 DM을 재생하면 오래된 엔드포인트로 되돌아간다(알림 중단). `ts` 기반
  단조 검사가 없다.

## 4. 아키텍처 전환 분석 — GitHub Pages → 맥

### 4.1 핵심 질문에 대한 답

> **"GitHub Pages를 경유하지 않고 맥을 서버로 쓸 수 있는가?"**

**절반은 예, 절반은 아니오.** §1.3의 두 역할로 나눠야 답이 나온다.

**역할 B(릴레이)를 맥으로 옮기는 것: 전적으로 가능하고, 오히려 권장된다.**
Nostr 릴레이는 프로토콜 설계상 *신뢰하지 않는* 구성요소다. 공개 릴레이 4곳을
내 맥 하나로 바꾸면 **제3자에게 새어나가던 메타데이터가 사라진다.** 탈취된
맥 릴레이가 할 수 있는 최대치는 열람(암호문)·삭제·지연·재생이며, 복호와
위조는 불가능하다 — NIP-59 seal 서명과 래칫의 AES-GCM AAD가 막는다.
삭제(침묵 검열)만 현재 무탐지이므로 F-14를 닫으면 된다.

**역할 A(코드 오리진)를 맥으로 옮기는 것: Zero Trust 요구와 정면충돌한다.**
맥이 `index.html`/`js/*.js`를 서빙하는 순간, 탈취된 맥은 악성 JS를 배포할 수
있고 그 JS는 IndexedDB에서 신원키를 읽어 반출한다. **프로토콜을 아무리 잘
설계해도 프로토콜을 구현하는 코드를 공격자가 쓴다면 의미가 없다.** 이건
구현 품질 문제가 아니라 논리적 귀결이다.

### 4.2 "코드 무결성 핀 고정으로 해결되지 않나?"에 대한 정직한 답

TOFU(Trust On First Use) 방식 — 최초 설치 시 전 파일의 SHA-256을 IndexedDB에
저장하고 이후 변경을 감지 — 은 **구현할 가치가 있지만 Zero Trust를 달성하지
못한다.** 검증자 자신이 같은 오리진에서 배달되기 때문에, 오리진을 장악한
표적 공격자는 "항상 통과한다고 답하는 검증자"를 서빙하면 그만이다.
서비스 워커도 마찬가지다 — 브라우저는 약 24시간마다 `sw.js`를 재확인하고
새 버전을 채택하며, **기존 SW가 이를 거부할 방법이 없다.**

따라서 TOFU 핀의 실제 가치는 다음으로 한정된다.
- ✅ 비표적 침해(사이트 변조, 배포 파이프라인 사고, 실수로 잘못된 빌드 배포) 탐지
- ✅ 조용한 교체를 **시끄럽게** 만들어 사용자가 알아챌 기회 제공
- ❌ 오리진을 노린 표적 공격 방어 — **불가능**

이 한계를 문서와 UI에 명시하지 않으면, 사용자에게 없는 안전을 파는 것이 된다.

### 4.3 웹을 유지하는 한 오리진 신뢰는 제거 불가능하다

진짜로 호스트 없는(host-free) 구성은 **브라우저를 떠나는 것**뿐이다 —
자산을 기기에 번들로 심은 네이티브 래퍼(Android WebView APK / iOS 사이드로드).
이는 현재 PLAN.md §1.1의 비목표("앱스토어 배포 없음", "HTML로 구현")와
충돌하므로 이번 범위 밖이지만, **"오리진 신뢰 0"을 원한다면 그 길밖에 없다는
사실**은 기록해 둔다.

### 4.4 권장 구성

```
┌──────────────────────────────────────────────────────────────┐
│  역할 A: 코드 오리진  — 맥이 아닌 정적 호스팅                 │
│  (GitHub Pages를 쓰기 싫다면 Codeberg / Cloudflare /          │
│   GitLab Pages / Netlify — 코드 변경 0, start_url이 상대경로)  │
│  + 엄격 CSP + TOFU 코드 핀 + 설정 화면의 빌드 지문 표시        │
└──────────────────────────────────────────────────────────────┘
                              │  HTML/JS (1회 설치 후 캐시)
                              ▼
                    ┌───────────────────┐
        Tailscale   │   폰 A  /  폰 B   │   Tailscale
        ────────────┤   (모든 평문·키)   ├────────────
                    └───────────────────┘
                              │  wss (암호문 kind 1059만)
                              ▼
┌──────────────────────────────────────────────────────────────┐
│  역할 B: 릴레이 + 푸시 헬퍼 — 맥 (신뢰하지 않음)              │
│  Tailscale Serve가 wss 종단 · 릴레이는 127.0.0.1에만 바인드    │
│  암호문 보관 7일 · 아카이브 별도 보관 없음 · 로그 최소화       │
└──────────────────────────────────────────────────────────────┘
```

**공개 릴레이 4곳은 완전히 제거된다.** 이것이 이 전환의 가장 큰 프라이버시
이득이다 — 수신함 pk·접속 IP·타이밍이 더 이상 제3자에게 가지 않는다.

### 4.5 전환 후 "맥 완전 탈취" 시 피해 산정

| 공격자가 **얻지 못하는** 것 | 근거 |
|---|---|
| 어떤 메시지의 평문도 | 래칫 세션 키는 두 폰 안에만 존재 |
| 어느 한쪽을 사칭할 능력 | 신원 개인키 부재 |
| 메시지 위조·변조 | NIP-59 seal schnorr 서명 + AES-GCM AAD |
| 과거 대화의 소급 복호 | 더블 래칫 (첫 왕복 이후 구간) |

| 공격자가 **얻는** 것 (수용된 위험) | 완화 |
|---|---|
| 암호문·크기·시각·수신자 pk = 메타데이터 | 원래 공개 릴레이가 보던 것이 내 상자로 이동. 보관 7일, 로그 최소화, FileVault |
| 메시지 지연·삭제 능력 | **F-14 수정으로 탐지 가능해짐** (신규) |
| 푸시 알림 스팸 | 내용은 고정 문자열이라 피싱 불가. `tag`로 1건 병합 (신규) |
| 서비스 정지 | 가용성 상실 — 수용. 맥이 꺼지면 대화 불가(공개 릴레이 폴백 제거의 대가) |

| 이 구성을 **깨뜨리는** 유일한 실수 | |
|---|---|
| 맥이 앱 코드까지 서빙하게 만드는 것 | → 악성 JS 배포 → 신원키 탈취 → **전면 붕괴**. 절대 금지. |

### 4.6 전환의 실질적 비용 (정직하게)

1. **두 폰 모두 Tailscale 상시 구동 필요.** 없으면 `*.ts.net`을 해석하지
   못해 대화 자체가 불가능하다.
2. **맥이 곧 단일 장애점.** 절전·재부팅·네트워크 단절 시 양쪽 모두 메시징
   중단. 공개 릴레이 4중화가 주던 가용성을 잃는다.
3. **iOS PWA + Tailscale VPN 조합은 실기기 검증이 필요하다.** 이 감사는
   정적 분석이므로 동작을 보증하지 않는다.

## 5. 현재 구현에서 **잘 되어 있는** 점

균형을 위해 기록한다. 아래는 감사 중 확인한 올바른 설계 결정들이다.

- **XSS 표면 없음**: 모든 사용자 입력이 `textContent`로만 렌더링된다.
  `innerHTML` 사용처는 `showUnsupported()`의 `""` 대입 한 곳뿐이다.
- **검증된 암호 프리미티브만 사용**: 자체 암호 구현이 없다. NIP-44 v2
  (Cure53 감사 완료)와 WebCrypto만 쓴다.
- **`sessDecrypt`의 사본-후-커밋 패턴**(`pfs.js`): 복호 실패가 래칫 상태를
  오염시키지 않는다. 변조·리플레이 내성의 핵심이며 정확히 구현되어 있다.
- **발행 가드**: `net.js`의 `publishWrap`이 `kind !== 1059`를 거부한다.
  평문 이벤트가 실수로 나갈 경로가 차단되어 있다.
- **알림 내용 없음**: 헬퍼는 복호 키가 없고 SW는 페이로드를 파싱하지 않으므로
  알림 피싱이 구조적으로 불가능하다. 좋은 설계다.
- **송신자 인증**: nostr-tools `unwrapEvent`가 seal 서명과
  `rumor.pubkey === seal.pubkey`를 검증한다. 발신자 위조 불가.
- **프리키 서명 바인딩**: 초대코드의 P-256 프리키가 신원키로 schnorr
  서명되어 있어, 프리키만 바꿔치기하는 공격이 차단된다.
- **PFS 예외 구간의 명시적 문서화**: PLAN.md §2가 첫 왕복 이전 구간의 한계를
  숨기지 않고 적어두었다.
